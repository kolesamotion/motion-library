# Процесс пополнения

## Первый реальный пример

Для действий с файлами и папками Google Drive использовать Google Drive-плагин в Codex. Корпоративный аккаунт пользователя: `basshybayev@kolesa.kz`. Синхронизацию локальной папки проекта между устройствами выполняет десктопное приложение Google Drive; это отдельный процесс от доступа плагина к материалам библиотеки.

Пользователь присылает ссылки или файлы и поручает добавить материалы. Проверить доступ подключённого корпоративного аккаунта к конкретной ссылке Google Drive. Email не доказывает доступ. Прочитать подходящий существующий фрейм Figma как образец оформления, полей, ссылок и демонстрации анимации.

На основе этого примера определить минимальный текстовый каталог и формат записи результата; до этого не создавать схему каталога и скрипты по догадкам.

## До записи

1. Определить материал, назначение и раздел библиотеки по запросу и источникам.
2. Проверить доступ к файлу или папке Drive. Для папки изучить состав материалов; не подменять ссылку папки случайным файлом.
3. Для локального файла без ссылки Drive уточнить место загрузки, если оно ещё не согласовано. Не менять права доступа самостоятельно и не создавать фиктивную ссылку скачивания.
4. Проверить существующие карточки Figma и каталог, когда он появится. Сопоставлять ID объектов Drive, узел Figma и контекст материала. Одного названия недостаточно; одна папка может содержать несколько анимаций.
5. Уже добавленный материал без изменений пропустить и сообщить об этом; при обновлении изменить существующую карточку. Неоднозначное соответствие уточнить до записи.
6. Если необходимый источник недоступен, сообщить конкретный объект и остановить зависимую запись без выдумывания данных.

## Запись и результат

1. Добавить или обновить карточку по проверенному образцу непосредственно в основной библиотеке. Сохранить доступные ссылки на тикет, раскадровку, демо, техническое описание и скачивание.
2. Сразу после внешней записи сохранить в текстовой записи результата дату, действие, ключ файла и ID узла Figma, ID и тип объекта Drive, постоянные ссылки и результат проверки. После введения каталога включать ID его записи. Не сохранять токены и временные подписанные URL.
3. При частичном выполнении записать созданные объекты и оставшиеся шаги. Перед повтором проверить внешнее состояние и продолжить по сохранённым ID без создания дубликатов.
4. Проверить текст, оформление и ссылки в Figma; проверить, что ссылка скачивания ведёт на доступный ожидаемый файл или папку Drive. Непроверенные пункты отметить явно.
5. Перед коммитом проверить локальные изменения: включать только относящиеся к задаче документацию, настройки, каталог и скрипты. Исключать медиа, секреты и выгрузки, включая анимационные исходники JSON/SVG.
6. Сообщить пользователю, что добавлено или обновлено, дать ссылку на карточку и указать ограничения проверки.

Откат коммита меняет только локальные файлы. Исправление Figma или Drive выполняется отдельно по сохранённым идентификаторам.

## Проверка при первом пополнении

- Ссылка на файл: материал определён корректно, карточка ведёт на этот файл.
- Ссылка на папку: состав материалов учтён, ссылка остаётся ссылкой на папку.
- Отсутствие доступа: зависимая запись остановлена, пользователь получил конкретную причину. Не менять права ради теста; без подходящего примера отметить сценарий как непроверенный.
- Повторная обработка: новая карточка не создаётся; изменения обновляют существующую.
- Частичное выполнение: повторный запуск учитывает сохранённые ID и проверяет состояние Figma.

При первоначальной настройке внешние сценарии ещё не проверены: нужны реальные материалы. Веб-сервис, фоновое наблюдение за Drive и двусторонняя синхронизация не входят в текущий процесс.
